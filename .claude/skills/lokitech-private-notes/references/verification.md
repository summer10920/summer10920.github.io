# 查證與驗證

寫私人筆記的信譽來自「每個斷言都查證過」。這份說明怎麼查、怎麼驗證範例、怎麼回報。

## 一、動筆前的查證

1. **規格與官方文件**：找該功能所在的規格章節（W3C／WHATWG／TC39）與 MDN 頁面，連結先收好，之後直接放進文章。
2. **支援度**：用 caniuse 的 feature 名稱（文章裡寫 `{% caniuse feature-name %}`），再查 MDN 的 Browser compatibility 與 Baseline 狀態；寫出各瀏覽器「從哪個版本開始」，不寫「大部分支援」。
3. **版本**：專案用到的套件或工具版本，用實際的 `package.json`、指令輸出或官方 release 頁確認；課程環境的主要版本見 `lokitech-15day-lecture-rules`。
4. **找痛點**：搜尋 Stack Overflow／MDN 討論／規格 issue，找出「讀者最常卡住的三個點」，這三個點一定要在文章裡有位置。
5. **查不到就不寫**：沒有把握的版本差異、行為細節寧可省略，或在回報裡標示「未驗證」。

## 二、範例要實際跑過

- 開場範例與每個結論用的範例，都要在真的瀏覽器裡開過，看到文章裡寫的結果。
- 驗證方式：把範例存成**暫存檔**（放在工作目錄之外或暫存資料夾，不要放進 `source/`），用瀏覽器直接開檔；或貼進使用者已開著的 `http://localhost:4000` 預覽中的文章觀察渲染。不要為了驗證另開伺服器、不要 `hexo clean`、不要在背景跑長時間任務。
- 觀察要具體：哪個元素有框、Console 印出什麼、DevTools Elements 看到什麼（例如 `#shadow-root`）。把觀察寫進「解析」。
- 支援度敏感的範例，至少在一個 Chromium 系瀏覽器實測；對其他瀏覽器的敘述以 MDN／caniuse 為準，並明說「依文件，未實測」。

## 三、文章本身的檢查

- 預覽用 `http://localhost:4000`：目錄（TOC）能掃懂、`mermaid` 有渲染、`note` 有闔上、圖片與連結可開、程式碼區塊檔名標題正常。
- 不自動建置；需要 `pnpm run build` 時請使用者同意再跑。

## 四、回報格式

交稿時用條列回報，簡短即可：

- 檔案與標題、最終行數。
- 目錄（`#` 與每章一句話）。
- **已驗證**：哪些範例實際跑過、哪些斷言對到哪份來源（規格、MDN、caniuse 的名稱與連結）。
- **未驗證／有疑慮**：沒實測的瀏覽器、沒有把握的版本差異。
- 需要使用者決定的事。
- 提醒尚未 commit。
