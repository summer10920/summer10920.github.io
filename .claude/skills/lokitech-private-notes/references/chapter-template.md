# 章節骨架與開場情境設計

## 開場情境怎麼設計

先寫情境，再決定章節。好的開場情境同時滿足：

1. **真實**：用有領域意義的結構與命名（`.card`、`.card__body`、`order-list`、`TourCard`），像是真的專案裡會出現的。
2. **夠複雜、不過度**：要有「結構有外殼、有插槽」「有巢狀」「有第三方內容」這類會讓簡單做法失效的地方，但不要塞進與主題無關的東西。
3. **一份到底**：後面各章都回到這份範例驗證，不要每章另起一份新的。
4. **能逐項勾選**：讀者可以對著結構逐個說出「這個會中、這個不會中」。

寫完範例，先列「現有做法」會怎麼壞（錯寫法 → 勉強寫法），再引出主題。

## 一個 `#` 大章的骨架

```md
# 章標題（用途或問題句，不只列 API 名）

本章在回答：<一兩句話，說清楚這章解決什麼問題、不講什麼>。

## 先看問題 / 最小示範

<用開場範例或最小完整範例。程式碼區塊要有檔名。>

## 解析：看到什麼、為什麼

- <對照畫面／Console／DevTools，一個重點一條，完整句子>
- <機制：瀏覽器或引擎怎麼運作>

## 易混點與邊界

- <最常被搞混的地方，附最小反例>
- <什麼情況下不成立>

{% note warning %}
**<一句話的陷阱>**
<為什麼，以及怎麼避開>
{% endnote %}

## 跟其他做法怎麼選（有替代方案時）

- <條件> → <選擇>
- 不要期待：<常見誤解>
```

## 全文的順序

1. 導言（2～3 句）＋ `<!-- more -->`，寫明閱讀順序。
2. `#` 為什麼會需要它（開場情境、現有做法的痛點、一句話點出主題）。
3. `#` 機制與語法（先純用，再組合；先拆開再合起來）。
4. `#` 易混點與層疊／邊界規則（會讓人踩雷的部分，用範例逐個講）。
5. `#` 定位：跟其他方案怎麼選（先教名詞與最小範例，再比較，最後給條件式結論）。
6. `# 瀏覽器支援`（視主題）：`{% caniuse %}`、各瀏覽器起始版本、備援做法、MDN／規格連結。
7. `# 專有名詞中英對照`：依出現順序，與大章對應的 `##` 底下分組。

## 圖的用法

- 關係、範圍、層級、流程才畫圖；用 `{% mermaid graph TB %}`，節點文字加雙引號，換行用 `<br/>`。
- 需要標「選中／未選中」「通過／被擋」時，用 `classDef` 配色：選中綠、上界藍、下界黃、未選中紅、其餘灰。
- 圖與正文要互相對得上（節點名稱用範例裡真實的 class 或元素名）。
- 一個情境一張圖，不要為了圖而圖；沒有辨識度的圖刪掉。

## 專有名詞怎麼寫

```md
# 專有名詞中英對照

## 為什麼會需要「範圍」

- 範圍（scope）
- 插槽（slot）

## 語法

- at 規則（at-rule）
- 範圍根（scope root）
```

依文章出現順序，每個 `##` 對應一個大章；一律用清單，不用表格。
