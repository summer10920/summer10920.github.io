# 深度標準與自查清單

這份是 `SKILL.md`「深度標準」的細則。目標：一篇私人筆記的豐富程度與 15 天講義相當。

## 什麼叫「有深度」

用 `css-scope.md` 當尺：它沒有一章是「名詞定義」。每章都是「情境 → 機制 → 結果 → 取捨」，而且每個結論都能用開場那份 HTML 驗證。

深度不是字數，是**每個斷言背後有多少可以檢查的東西**：

- 一個範例（完整、能跑）
- 一個結果（畫面、Console、DevTools 看到什麼）
- 一個機制（為什麼會這樣）
- 一個邊界（什麼時候不成立）
- 一個來源（規格、MDN、caniuse、自己跑的輸出）

## 空洞寫法 vs 有深度的寫法

### 開場

- 空洞：「`@scope` 是 CSS 的新功能，可以限定樣式範圍，非常方便。」
- 有深度：貼一份真實的產品卡片 HTML（外殼有頭像、封面、工具列圖示，`.card__body` 是 CMS 灌進來的插槽），說明需求「外殼的圖加框、插槽裡的圖一張都不要動」，再示範 `.card img` 為什麼錯、路徑枚舉為什麼脆弱。

### 機制

- 空洞：「同權重時，後面的規則會贏。」
- 有深度：說明 `@scope` 不增加選擇器權重，但同權重時「離 scope root 近的贏」，給一個巢狀主題（`.light` 裡放 `.dark`）的範例，逐行說明誰贏、為什麼，再說明什麼情況下仍然是來源順序決定。

### 對照其他方案

- 空洞：「BEM、CSS Modules、Shadow DOM 也能做到類似的事。」
- 有深度：每個方案先用最短的原生範例講「是什麼、屬於約定／建置工具／瀏覽器哪一層」，再回到開場的卡片情境看它能不能解、代價是什麼，最後給「怎麼選」的條件清單與「不要期待什麼」。

### 支援度

- 空洞：「現代瀏覽器大多支援。」
- 有深度：`{% caniuse feature %}`，再寫 Chromium、Safari、Firefox 各自從哪個版本開始、Baseline 狀態、舊環境的備援做法，並附 MDN 連結；偽類與 at 規則支援度不同時分開寫。

## 每章的最小內容

一個 `#` 大章要有：

1. 一兩句「本章在回答什麼」（不是「本章目標」）。
2. 至少一個完整、有檔名的範例（或明確引用開場範例）。
3. 範例的解析：看到什麼、為什麼。
4. 至少一個易混點或邊界。
5. 若涉及選擇，給條件式的結論。

## 自查清單（交稿前逐條打勾）

- [ ] 開場是真實情境與完整範例，不是定義。
- [ ] 沒有 `foo`／`bar`／`test` 這類玩具命名。
- [ ] 每個概念都走完「痛點 → 示範 → 解析 → 易混／邊界 → 取捨」。
- [ ] 至少有一組「錯／勉強／正確」對照，並說明差異。
- [ ] 機制有講（不只是怎麼寫）。
- [ ] 範例實際跑過；斷言能對到規格、MDN 或輸出。
- [ ] 版本號與支援度有查證，連結都能開。
- [ ] 有 `mermaid` 圖說明範圍、層級或流程（至少一張，且有辨識度）。
- [ ] 有「怎麼選」與「不要期待什麼」。
- [ ] 重複的長範例已用標註摘錄取代。
- [ ] 沒有「非常強大」「很方便」這類形容詞取代說明。
- [ ] `# 瀏覽器支援`（視主題）與 `# 專有名詞中英對照` 都有。
- [ ] 行數合理（單一主題通常 400～900 行；不到 300 行要回頭檢查哪裡帶過）。
- [ ] 格式：不用表格、粗體裡沒有行內碼、`note` 有結尾、標題不跳層、front matter 用 `tag:`。
- [ ] 回報裡列出驗證了什麼、沒驗證什麼。
