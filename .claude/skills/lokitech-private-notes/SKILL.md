# 私人筆記（個人學習歸類）

適用：`source/_posts` 裡**新寫**的個人技術筆記——把一個主題講到可以回查、可以拿去做決定的程度。
不是課堂講義（→ `lokitech-15day-lecture-rules`），也不是舊文潤稿（→ `lokitech-post-polish`）。

**這份技能最重要的一句話：深度要和 15 天講義一樣。** 一篇私人筆記讀完，讀者要能（1）看懂這東西解決什麼真實問題、（2）知道它怎麼運作、（3）能照範例跑出同樣結果、（4）知道什麼時候不該用、（5）知道跟其他方案怎麼選。做不到這五點就是空洞，不能交稿。

## 先讀（動筆前，缺一不可）
1. 根目錄 `AGENTS.md`：協作與終端政策、front matter 與分類慣例、撰寫規則。
2. `scaffolds/tagslang.md`：標籤語法（`note`、`mermaid`、`caniuse`、`blockquote`、`post_link`…），不要憑記憶寫。
3. **參考成品** `source/_posts/css-scope.md`（約 640 行）：照它的密度與章法。重點看：開場的完整 HTML 情境、「錯／勉強／對」三段對照、`mermaid` 標出選中與未選中、每章開頭一句「本章在回答什麼」、對照章先教名詞再比較、支援度章與專有名詞章。
4. 深度基準：再讀一節 15 天講義（例如 `lokiTech-15day-03-css.md` 的「選擇器與權重」或 `lokiTech-15day-06-js-basics.md` 任一章），感受「觀念 → Demo → 解析」要寫到多細。
5. 本技能的三份細則（需要時才開）：
   - `references/depth-bar.md`：深度標準、空洞寫法對照、自查清單。
   - `references/chapter-template.md`：每一章的骨架與開場情境怎麼設計。
   - `references/verification.md`：怎麼查證事實與驗證範例，以及回報格式。

## 這類文章是什麼、不是什麼
- **是**：痛點 → 機制 → 易混點 → 與其他方案的取捨 → 支援度 → 名詞。給有基礎的自己或同程度讀者回查。
- **不是**：一步步跟著做的教學、講師備課筆記、API 清單、官方文件的翻譯摘要、沒有立場的「比較表」。
- 讀者預設有基礎，但**專有名詞仍要講清楚**（不要假設一定知道 CSS Modules、Shadow DOM），也**不要把原生 API 寫得像某框架功能**。

## 深度標準（硬性，逐條對照）
1. **開場是情境，不是定義。** 第一章用一份夠真實的完整範例（完整 HTML／元件結構，有領域意義的命名如 `card`、`order`、`tour`，禁止 `foo`／`bar`／`test1`），先讓讀者看到「現有做法為什麼痛」。
2. **每個概念走完整的弧線**：痛點 → 最小可跑示範（完整檔案、程式碼區塊帶檔名）→ 解析（對照畫面、Console、DevTools 看到什麼）→ 易混點與邊界 → 與替代方案的取捨。缺任何一拍就是空洞。
3. **一定有對照**：至少一組「錯／勉強／正確」（或舊寫法／新寫法）並排，並說明差在哪裡、為什麼。
4. **講機制，不只講寫法**：這東西在瀏覽器或引擎裡怎麼運作（例如權重怎麼算、誰贏、為什麼會這樣），讀者才能自己推理沒寫到的情況。
5. **有證據**：每個斷言都能追溯到跑過的輸出、規格章節、MDN 或 caniuse；版本號、支援度寫到精度，不憑印象。
6. **用圖說關係**：範圍、層級、流程、誰選中誰沒選中，用 `mermaid`（`{% mermaid %}` 標籤）配色標出。
7. **有決策**：有替代方案就寫「怎麼選」（條件 → 選擇）與「不要期待什麼」。沒有立場的比較等於沒寫。
8. **收尾齊全**：`# 瀏覽器支援`（視主題；用 `{% caniuse %}` 加 MDN `blockquote` 連結）與 `# 專有名詞中英對照`（必有）。
9. **密度**：不以字數為目標，但單一主題通常 400～900 行。寫完不到 300 行時，回頭找「哪個概念只用一句話帶過」。

## 禁止的空洞寫法
- 只列 API／屬性清單，沒有情境、沒有結果。
- 用 `foo`／`bar`、`.box`／`.item` 這類玩具範例撐篇幅。
- 「非常強大」「很方便」「更靈活」這類形容詞取代機制說明。
- 「看範例就知道」：範例貼了卻不說畫面或輸出是什麼、為什麼是這樣。
- 對照章只有名詞定義，沒有最小範例，也沒說各自屬於約定／建置／瀏覽器哪一層。
- 同一份長 HTML 貼三遍；重複的段落用標註摘錄或「同開場 `page.html`」代替。
- 沒驗證就寫版本與支援度；引用規格卻沒給連結。
- 結尾「總結」把前文重述一遍卻沒有取捨。

## 工作流程
1. **確認題目**是私人筆記，不是講義或潤稿；讀 `AGENTS.md`、同主題舊文，避免重複。
2. **查證**（見 `references/verification.md`）：規格、MDN、caniuse、版本；找出「讀者最常卡住的三個點」。
3. **定目錄**：標題用途或問題句；每個 `#` 寫一句「本章在回答什麼」；列出每章的示範檔與要驗證的結論。題目大或不確定時，先把目錄給使用者看，確認再寫。
4. **設計開場情境**（見 `references/chapter-template.md`）：先把完整 HTML／元件寫好，再決定各章拆在哪裡。
5. **寫作**：按章成稿，每章都走完深度標準第 2 條的弧線；邊寫邊檢查「先純用、再組合」「先解釋名詞、再比較」。
6. **驗證**：範例實際跑過、斷言對得上來源（見 `references/verification.md`）；不自動執行 `hexo`／`pnpm` 等，預覽用使用者開著的 `http://localhost:4000`。
7. **自查**（`references/depth-bar.md` 的清單）：逐條對照，不過關就補，不要交半成品。
8. **回報**：給目錄、行數、驗證了什麼與沒驗證什麼、用到的外部來源；改動留在工作區，經使用者同意再 commit。

## Front matter、檔名與格式
- 用 `scaffolds/post.md` 慣例：封面圖、2～3 句導言、`<!-- more -->`（之前不放 Hexo 標籤）。導言要寫出閱讀順序（痛點 → 機制 → 易混點 → 對照 → 支援度 → 名詞）。
- 分類掛技術層（例如 `前端` > `HTML/CSS`）；要藏進私人用 `工具與其他` > `私人` 或 `hidden: true`。欄位是 `tag:`，只放技術名、不寫版本號。
- 檔名 `技術-主題` 或 `技術-版本-主題`（小寫、連字號、無日期）。標題以**用途／痛點**為主，不只列 API 名。
- 一篇 3～6 個 `#`，不跳層，單一小節不要硬拆成只有一個子標題；`#` 底下用 `##`／`###`。
- 收尾固定：`# 瀏覽器支援`（視主題）→ `# 專有名詞中英對照`（依出現順序、與大章對應的 `##` 底下分組、不用表格）。**不要**講義的作業、重點回顧、選讀標記，也不要文末手寫上一篇／下一篇。
- 文體：繁體中文；術語保留英文，首次出現給短解釋；用「你」可以，但口吻是筆記／歸類，不是「今天課堂會教…」。
- 不用表格（改用清單）。行內碼只包真正的程式碼片段；**不要把行內碼放進粗體裡**。
- 程式碼區塊語言後接檔名（`` ```css card.css ``）、註解用繁中、範例要能對上正文情境；重複的 HTML 不要貼第二遍。
- `note` 一定要有 `{% endnote %}`；`mermaid` 用標籤，節點文字加雙引號、換行 `<br/>`，需要標選中／未選中時用 `classDef` 配色；站內連結用 `{% post_link 檔名 文字 %}`。
- 說到 DevTools 或瀏覽器行為時，寫可操作的觀察點（例如 Elements 面板裡的 `#shadow-root`、Console 輸出什麼）。
